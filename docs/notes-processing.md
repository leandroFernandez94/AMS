# AMS — Notes Processing

This document is the anatomy of an AMS note and the full story of its
lifecycle: how a write is validated and locked, how updates and deletes are
routed, and how the index makes it all searchable. Read it when you integrate
with the Write API or the `record_note` / `delete_note` MCP tools, or when you
need to reason about concurrency in the vault. System topology, authentication
and configuration live in [architecture.md](architecture.md); daemon
operations in [retrieval-runbook.md](retrieval-runbook.md).

The short version: a note is one deterministic Markdown file at
`<type>s/<id>.md`; every mutation runs through validation, a path-scoped
in-memory lock and a dirty-flag store; a scheduler embedded in the API process
drains those flags into the QMD index on a cron (default every 2 minutes), and
search reads that index — never the vault directly.

Related runbooks: [e2e-runbook.md](e2e-runbook.md) (end-to-end loop),
[quickstart.md](quickstart.md) (first run).

## Anatomy of a note

A note is a single Markdown file: a YAML frontmatter block, one blank line,
then a free-form markdown body. The body is preserved verbatim (only CRLF is
normalized to LF and outer blank lines trimmed) — no section structure is
enforced, ever.

Frontmatter fields, in the exact fixed order the serializer emits them
(`packages/shared/src/note.ts`):

| Field | Type | Purpose | Required |
|---|---|---|---|
| `id` | string | canonical slug derived from `title`; names the file | yes |
| `title` | string | non-empty human title; the source of the `id` | yes |
| `date` | string | ISO `YYYY-MM-DD`; stamped today UTC when the caller omits it | yes |
| `type` | string | lowercase, starts with a letter (`decision`, `learning`, `pattern`, ...) | yes |
| `topic_key` | string | identity key for upsert routing — lowercase segments joined by `/` | no |
| `tags` | string[] | lowercase kebab-case labels; semantic relations between notes | yes (defaults to `[]`) |

There are no created/updated timestamps — `date` is the only date, and it is
whatever the writer set (or today UTC).

The serialization is deterministic: fixed key order, LF line endings, the
body after a single blank line. Round-tripping a note through parse +
serialize is stable, which is what makes idempotent upserts possible.

Example note:

```markdown
---
id: use-qmd-for-retrieval
title: Use QMD for retrieval
date: 2026-10-20
type: decision
topic_key: architecture/retrieval
tags:
  - retrieval
  - indexing
---

QMD provides hybrid lexical + vector search out of the box. Embeddings are
generated by the scheduler; agents never call QMD's write surface directly.
```

### Path derivation

The vault path is `<type>s/<id>.md`: the directory comes from the type via a
naive `+s` pluralization (`decision` → `decisions/`). Irregular plurals are
not handled — pick type names that pluralize cleanly.

### Slug rules

The `id` is derived from the title (`slugify`, `packages/shared/src/slug.ts`):

1. NFKD normalize + strip combining marks (`ñ` → `n`, `é` → `e`).
2. Lowercase.
3. `&` becomes ` and `.
4. Every run of non-`[a-z0-9]` characters collapses to a single `-`.
5. Leading and trailing dashes are trimmed.

A title with no usable alphanumeric content produces an empty slug, and the
write is rejected with a `400` validation error.

## Lifecycle

### Write (create)

```
1. Validation       JSON → NoteInputSchema → date ISO → buildNote
                    (id = slug(title)) → frontmatter schema + coherence;
                    any failure answers 400, nothing written.
2. Path             <type>s/<id>.md
3. Lock             acquire the path-scoped write lock (see Locking)
4. Persist          serializeNote → write the file atomically at its path
5. Dirty mark       <vault>/.ams/dirty.json records the changed path
6. Scheduler        the embedded IndexScheduler drains dirty flags
                    (cron, default every 2 minutes)
7. Index            execFile: qmd update + qmd embed → on success the
                    drained flags are cleared
```

The write itself never indexes inline — indexing is model-bound and slow, so
it happens asynchronously. A note is durable immediately after step 4 but
becomes searchable only after step 7 succeeds (force it with
`POST /admin/reindex`). The response is `201` for a created note, `200` for
an updated one; the MCP tool renders `Note recorded: <id> at <path>`.

### Update (upsert)

Three routes, in order of precedence:

1. **`topic_key` routing (intended update).** When a payload carries a
   `topic_key` that an existing note already owns, the request updates *that*
   note — even if the new title or type changes the canonical id and path.
   The rebuilt note is written at its new path first, then the old file is
   unlinked (write-then-unlink): no orphan files, and a crash between the two
   steps leaves at worst a duplicate that the next keyed write re-collapses.
   The response carries `moved_from` when the path changed; the MCP tool
   renders `Note updated: <id> at <path> (moved from <old path>)`. Both the
   old and new paths are dirty-marked so the index drops the stale entry.
2. **Title collision (no `topic_key`).** A create landing on an occupied
   canonical path is a conflict: `409 note_exists` with the occupying note's
   full raw on-disk content in the response body — nothing was written. This
   is a normal protocol outcome, not an error: retitle the note, or retry the
   exact same call with `overwrite: true` to replace it.
3. **`overwrite: true`.** Forces the replacement; answers `200` with
   `created: false`.

A `topic_key` update only conflicts when a *different* note occupies the
destination path — the note itself (or a duplicate carrying the same key) is
exactly what the update intends to replace.

### Delete

`DELETE /notes/:path` takes a vault-relative path (the one `search_memory`
shows in parentheses). Structural validation rejects, with `400`:

- empty paths, backslashes, absolute paths, or a missing `.md` suffix;
- empty segments and `..` segments (vault escape);
- any dot-directory (`.ams/`, `.qmd/`) — system state, never note content.

Then: a fast-fail `404` **before** queueing on the lock (a wrong path must
not wait behind a concurrent writer), the path lock, a re-check under the
lock (`404` if the file vanished while waiting), unlink, and a dirty mark.
Unparseable hand-written files are deletable too — their raw content travels
back in the response so an accidental delete stays recoverable.

A delete fires one **immediate, best-effort scheduler tick** (a failed tick
never fails the already-durable delete; the periodic schedule remains the
real guarantee). The note disappears from search results after the next
successful index cycle — `qmd update` drops documents whose files are gone.

## Locking

Agents can fire parallel writes at the same logical note. The Write API
serializes them with an **in-memory, path-scoped** lock
(`packages/api/src/lock.ts`):

- **Path-scoped**: concurrent writes to *different* notes never block each
  other; contention exists only per vault-relative path.
- **FIFO per path**: waiters queue in arrival order, so no request starves
  under sustained load.
- **TTL safety net**: each acquisition arms a fresh timer
  (`AMS_LOCK_TTL_MS`, default 5000 ms). A holder that crashes or hangs
  without releasing cannot deadlock the path — the lock auto-expires and the
  next waiter proceeds. Waiting is the normal path for callers; a stuck
  holder costs at most one TTL.
- **Rename safety**: a `topic_key` write that renames a note acquires both
  the old and new path locks **in sorted order**, which serializes crossing
  renames and prevents deadlock. If the note moves between the pre-lock
  lookup and lock acquisition, the whole sequence retries with fresh state
  (up to 3 attempts); sustained movement surfaces as a retryable
  `503 write_conflict`.
- **Single replica by design**: the lock lives in process memory. A second
  API replica breaks lock correctness — see the operational caveats in
  [architecture.md](architecture.md).

## Read path (search)

```
agent → search_memory ──► QMD daemon :8181 (JSON-RPC, initialize handshake + session-id)
                           hybrid lexical+vector, RRF fusion → hits with docid #abc123
agent → get_memory(#abc123) ──► QMD get → full note body
```

Asymmetry to remember: `get_memory` needs the **docid** returned by
`search_memory`; a vault-relative path does not resolve. Daemon operations
(model cache, rerank policy, lifecycle) are covered in
[retrieval-runbook.md](retrieval-runbook.md).

## Indexing

Writes never pay the cost of indexing inline. Instead every mutation marks
the affected path in `<vault>/.ams/dirty.json` (atomic writes, marks
serialized on a single chain), and the **IndexScheduler — embedded in the
API process, not a separate daemon** — drains the store:

- **Schedule**: node-cron, `AMS_INDEX_CRON`, default `*/2 * * * *` (every 2
  minutes); `AMS_INDEX_ENABLED=false` is the kill-switch (manual reindex
  still works).
- **Cycle**: drain the dirty snapshot → `qmd update` (refresh the lexical
  index) → `qmd embed` (vector embeddings); the daemon picks the changes up
  without a restart. Collection scoping (`AMS_QMD_COLLECTION`) applies to
  `embed` only — `qmd update` re-scans every registered collection.
- **Failure contract**: flags are cleared only after a fully successful
  cycle, so a failed tick (or an API restart mid-cycle) simply retries the
  next tick. Dirty state survives downtime because it is a file in the vault.
- **Manual**: `POST /admin/reindex` runs one identical cycle immediately
  (`503` when the scheduler is unwired or the cycle fails).
